# 공통 단원 템플릿

모든 단원(`units/uNN-이름/`)은 아래 구조를 따릅니다. `npm run lint:units` 가 **파일이 있는지** 확인합니다. (구조 점검일 뿐 교육적 품질을 보증하지 않습니다 → [quality.md](quality.md))

```
units/uNN-이름/
  README.md              단원 지도: 목표 시간, 순서 표, 완료 체크리스트
  01-problem.md          ① 새 개념이 필요한 구체적 문제 (현재 코드로 해결 안 되는 상황)
  02-prereq.md           ② 선수 지식 (짧게. 이미 배운 것은 링크). 스스로 확인 문제
  03-concept.md          ③ 개념 + 비유 뒤 정확한 기술적 의미
                           · 문법 / API 가 정한 형식 / 개발자의 설계 선택 구분 표
                           · 이 코드가 없으면 어떻게 되나 표
  04-example.md          작동하는 짧은 예시 읽기 (빈 화면에서 시작하지 않기)
  predictions.md         ④ 예측 (P1, P2 ... 형식. 실행 전에 작성)
  05-implement.md        ⑤ 직접 구현 과제와 쓰기 전 생각
  06-experiments.md      ⑦ 오류 실험 (AI 가 쓴 그럴듯한 틀린 코드 리뷰 포함)
  07-apply.md            ⑧ 조건이 바뀐 응용 (도움 수준을 줄인 상태)
  08-recall-explain.md   ⑧ 회상(2~3단원 전) + 설명 루브릭
  misconceptions.md      흔한 오개념 3개 + 예측 질문
  reflection.md          자기 말로 설명 (자리표시 문구가 남으면 "아직")
  FEEDBACK.md            실제 걸린 시간, 막힌 곳, 부족한 설명, 지루한 곳, 힌트
  unit.ts                단원 정의 + 자동 검사(⑥). 기대값/실제값/읽을 개념/고칠 곳을 돌려줌
  start/                 검증된 시작 코드 (미완성 TODO → 교육용 오류). 직접 고치지 않음
  example/               작동하는 예시 코드
  experiments/           오류 실험용 코드 (e1, e2 ...). 학습자 코드와 분리
  hints/1-concept.md     힌트 1단계
  hints/2-pseudo.md      힌트 2단계
  hints/3-partial.md     힌트 3단계
  work/                  (npm run begin 이 start/ 에서 복사해 만듦) 내 코드. 도구가 덮어쓰지 않음
solutions/uNN-이름/      정답 코드 + EXPLANATION.md (학습 화면과 분리. 보안 장치 아님)
```

## 단원 한 번의 흐름 (사람이 하는 일)

| # | 단계 | 학습자가 하는 일 | 도구 |
|---|---|---|---|
| 1 | 문제 | 지금 코드로 안 되는 것을 본다 | 01 |
| 2 | 선수 지식 | 필요한 기초 확인, 부족하면 보충 | 02, docs/foundations |
| 3 | 개념 | 왜 필요한지 자기 말로 말해 본다 | 03 |
| 4 | 예시 읽기 | 작동하는 예시의 줄마다 무슨 일을 하는지 | 04 |
| 5 | 예측 | **실행 전에** 결과를 `P1:` 형식으로 적는다 | predictions.md |
| 6 | 구현 | 핵심 코드를 직접 쓴다 (TODO) | work/ |
| 7 | 검증 | 통과·실패. 실패 메시지의 기대/실제/개념/위치 | `npm run check` |
| 8 | 관찰 | 실행 기록을 한 단계씩 보며 예측과 비교 | `npm run view` |
| 9 | 오류 실험 | 틀린 코드를 읽고 예측 후 돌려 원인을 찾는다 | `npm run experiment` |
| 10 | 응용 | 조건이 바뀐 문제를 줄어든 힌트로 | `--apply` |
| 11 | 회상·설명 | 이전 개념을 꺼내고, 자기 말로 설명 | reflection.md |

## 도움 수준을 줄이는 규칙 (스캐폴딩 페이딩)

- 단원 안: 작동 예시(전부 있음) → 구현 TODO(힌트 3단계) → 응용(힌트 1단계만) → 회상(힌트 없음)
- 단원 간: 앞 단원의 코드를 뒷 단원에서 점점 빈칸으로 요구한다 (예: U03 의 반복 루프를 U04 에서 그래프 없이 다시 쓰게 함)

## 검사 작성 규칙

1. 출력 문구가 아니라 **모델에 보낸 messages, 도구 실행 여부, 상태 변화** 같은 공개 동작을 검사한다.
2. fake LLM 이나 하네스가 학습자가 구현할 일을 대신하지 않는다 (예: 기록 관리는 학습자 몫).
3. 실패 메시지는 기대값 · 실제값 · 읽을 개념(문서#절) · 고칠 곳(파일:줄) 을 갖는다. 정답 코드를 노출하지 않는다.
4. 검사는 실행 기록(`runs/`)을 남기고, 학습 화면이 같은 기록을 그린다.
5. `start/` 는 모든 기본 검사가 **교육용 TODO 오류**로 실패해야 하고, `solutions/` 는 모두 통과해야 한다 (`npm run selftest`).
6. 단원마다 "그럴듯하지만 틀린" 실험 코드를 최소 1개 넣고, 그것이 실패하는지 selftest 로 확인한다.
