# 3. 개념: 모델은 기억하지 않는다

> **지금 하는 일: 개념 읽기 · 작성 없음**
>
> 여기에 답을 적지 않습니다. 표를 읽고 [실행 예제 안내](04-example.md)로 이동하세요.

**이렇게 생각해 보세요:** system = 상담원의 업무 매뉴얼, user = 손님의 말, assistant = 상담원의 답, messages = 그 말을 모은 공책입니다. 공책에 답을 옮겨 적는 사람은 우리 프로그램입니다.

[작성 위치 안내](00-workspace.md) · [단원 목차](README.md) · [실행 예제](example/ex2-followup.ts)

## 먼저 공책으로 생각해 보기

오늘은 예약 처리를 하지 않고 **방을 추천받고 이어 묻기**만 합니다.

```text
나:   4명이 쓸 방 찾아 줘.
모델: A방과 B방이 있어요.
나:   그중 가장 저렴한 곳은?
```

매번 다른 상담원에게 전화한다고 생각하세요. 새 상담원에게 마지막 말만 하면 “그중”이 무엇인지 모릅니다. 이전 대화가 적힌 **공책**을 함께 건네야 합니다. 그 공책이 `messages` 배열입니다.

`role`은 공책에 적는 **말한 사람의 이름표**, `content`는 **그 사람이 한 말**입니다. `assistant`라는 별도 저장소가 있는 것이 아닙니다. 모델이 한 말도 같은 배열에 넣습니다.

| 시점 | 배열 안에 들어 있는 메시지 | 개수 |
|---|---|---|
| 새 대화 시작 | system(개발자가 정한 업무 지침) | 1 |
| 첫 질문 추가 → 모델에게 보냄 | system → user(방 찾아 줘) | 2 |
| 답을 받아 우리 코드가 기록에 추가 | system → user → assistant(추천한 방들) | 3 |
| 후속 질문 추가 → 전체를 다시 보냄 | system → user → assistant → user(그중 싼 곳은?) | 4 |
| 두 번째 답까지 기록 | system → user → assistant → user → assistant | 5 |

```ts
const reply = await chat(messages); // 답 하나를 받음. messages는 그대로
messages.push(reply);               // 우리 코드가 답을 배열에 추가함
```

답을 기록해야 다음 호출에도 추천 목록을 보여 줄 수 있습니다. `system`은 배열 맨 앞에 한 개만 두지만, 전체 기록을 보내므로 **매번 함께 전달**됩니다.

## 모델은 기억하지 않는다

LLM 을 부르는 것은 **함수 호출과 비슷**합니다. 입력(messages)을 주면 출력(답 한 개)이 나옵니다. 함수가 지난 호출을 몰래 기억하지 않듯, 모델도 지난 호출을 기억하지 않습니다.

> 비유: 매번 처음 만나는 상담원에게 전화하는 것과 같습니다. 어제 한 이야기를 오늘 이어 가려면, 내가 어제 이야기를 다시 읊어 줘야 합니다.
>
> **이 프로젝트의 동작:** `chat(messages)`는 전달받은 메시지만 봅니다. 이전 호출의 기록을 자동으로 가져오지 않으므로 **우리 프로그램이 기록을 보관하고 전달**합니다. 다른 서비스에서는 기록 관리를 대신해 주기도 합니다.

## messages 는 대화 전체다

모델에 보내는 것은 질문 한 줄이 아니라 **메시지 배열**입니다.

```ts
[
  { role: "system",    content: "너는 스터디룸 예약 도우미다. ... 방 목록: ..." },
  { role: "user",      content: "내일 오후에 4명이 쓸 방 찾아 줘" },
  { role: "assistant", content: "4명이 쓸 수 있는 방입니다: ..." },
  { role: "user",      content: "그중 가장 저렴한 곳은?" },
]
```

모델은 이 배열 **전체**를 읽고 마지막에 올 assistant 메시지를 만듭니다. "그중"이 무엇인지는 배열 안에 있는 세 번째 메시지를 보고 압니다. 그 메시지가 배열에 없으면 알 방법이 없습니다.

따라서 후속 질문을 이해시키는 방법은 하나입니다.

1. 지금까지의 대화(기록)를 들고 있다가
2. 새 질문을 **기록 뒤에 붙여서**
3. 전체를 다시 보내고
4. 받은 답도 **기록에 붙여 둔다** (다음 질문을 위해)

## role 은 누가 한 말인가

| role | 누가 한 말 | 이 프로젝트에서 |
|---|---|---|
| `system` | 모델에게 주는 역할과 규칙 | 방 목록과 "예약 도우미다" 안내. 맨 앞에 한 번 |
| `user` | 사람(사용자) | 사용자의 질문 |
| `assistant` | 모델 | 모델이 한 답. 우리가 기록에 붙여 둔다 |
| `tool` | 도구 결과 | U02 에서 배웁니다 |

## 코드의 각 부분: 무엇이 문법이고, 무엇이 API 규칙이고, 무엇이 내 선택인가

| 구분 | 예 | 바꿔도 되나? |
|---|---|---|
| **언어 문법** (TypeScript) | `async`/`await`, `[...history, x]`, `Promise<Turn>` | 문법이라 정해져 있음 |
| **이 프로젝트의 호출 약속** | 메시지는 `{ role, content }`, `Message` 타입의 role은 네 가지, `chat(messages)`는 assistant 메시지 하나를 돌려줌 | 이 프로젝트 코드와 맞춰야 함. 모든 API가 같은 형식인 것은 아님 |
| **개발자의 설계 선택** | 기록을 함수 인자로 받고 새 배열로 돌려줌 / `{ messages, answer }` 로 묶어 돌려줌 / 질문마다 system 을 다시 넣지 않음 | 바꿀 수 있다. 장단점이 있다 |

## 이 코드가 없으면 어떻게 되나

| 빼는 것 | 결과 |
|---|---|
| user 질문을 기록 뒤에 붙이기 | 모델이 새 질문을 아예 못 본다 |
| 받은 assistant 답을 기록에 붙이기 | 다음 질문 때 "그중" 의 근거가 없다 → "찾을 수 없다" (실험 e1 이 바로 이 경우) |
| 기록 전체를 다시 보내기 (질문만 보내기) | 매번 새 대화가 된다 |
| 새 대화마다 새 배열 만들기 (전역 변수에 계속 쌓기) | 다른 대화가 섞인다 (실험 e2) |
| `await` | 답 대신 Promise를 받는다. TypeScript도 `reply.content` 접근을 오류로 알려 준다 |

## 설계 선택: 기록을 어떻게 돌려줄 것인가

읽기 예제의 `push`는 배열 자체를 바꿉니다. 직접 구현에서는 한 단계 더 나아가 **원본을 보존하는 방식**을 연습합니다. `push`가 잘못된 문법인 것은 아닙니다.

```ts
const old = ["업무 지침", "첫 질문"];
const next = [...old, "첫 답"];
// ...old: old 안의 값을 하나씩 펼쳐 넣는다
// old는 그대로, next는 첫 답이 추가된 새 배열
```

`ask` 는 기록을 **제자리에서 고치지 않고**, 이어 붙인 **새 배열**을 돌려줍니다.

```ts
const next = [...history, { role: "user", content: question }]; // history 는 그대로
```

- 장점: 호출하는 쪽의 기록이 몰래 바뀌지 않아서, 같은 기록으로 "만약 다른 질문을 했다면"을 시험해 볼 수 있다. 나중에 되돌리기(U10)도 쉬워진다.
- 단점: 배열을 매번 새로 만든다 (이 규모에서는 문제 없음).

> 이 선택은 정답이 하나가 아닙니다. 하지만 이 단원의 검사는 "넘긴 history 를 바꾸지 않는다"를 요구합니다. 그 이유를 reflection.md 에 자기 말로 써 보세요.

## 필요 없는 대화는 지워도 되나?

실제 앱은 오래된 기록을 줄이거나 요약하기도 합니다. 다만 다음 질문에 필요한 정보는 남겨야 합니다. 추천 목록을 지우면 “그중”을 이해할 근거가 없어집니다.

이 단원에서는 삭제나 요약 없이 **두 번의 대화를 빠짐없이 이어 보내는 것**만 연습합니다.
